## 2. 这一轮交了什么

到这里可以停，如果要知道做完了什么、故意没做什么。

目标是把数仓里核对过的一只 SKU 放进现有商品库。没有新开页面，也没有 `/mvp`。M9 只是目前资料最全的一只，不是单独一个产品。

页面现在是左导航六个模块，名字对齐 `docs/20261026-*.jpg`。没打开商品时，后五个不能点，也不会跳进写死的 M9。

- 主数据：原来的字段和变体表还在。上面多一块「数仓核对的这一只」，因为样例变体表里没有 `BP265-NR71BA`。
- 全渠道：横表，列是独立站、Amazon、Walmart、TikTok。TikTok 写未接入。独立站页面属于相邻 SKU `BP266-NR71BA`。表下面仍是整只 SPU 的样例经营，标题写了「整只 SPU」。

## 3. 改页面时先守的几条

到这里可以停，如果只改文案和布局，不补新数据。

- 缺的数写「未接入」「无法确认」或「资料冲突」。不补 0，不用原型图上的演示数填空。原型里的完整度 92%、BSR、社媒数、386 个素材库都没有对上的数据，不要做回去。

- oss key 不是网址。不要拼域名，不要做假预览。
- 设计任务挂在 `SPU000168`，不挂在 `BP265-NR71BA`。文件名里有托腹带、M7A&M10、内衣集合页。留着，页面上已经说明没有算到这只 SKU。
- 问商品只认包装、价格、评论、说明书。不要用问题开头几个字做匹配。之前那样会把「多少钱」答成评论。

- 路由保持现在这六个。不要再加独立的 MVP 页。
- 请求链路仍是 NestJS 加 Postgres 里的样例库。不要为了这一只 SKU 改 API 或灌进 Postgres，除非单独决定这么做。

## 5. 再补一张表时，键怎么走

到这里可以停，如果不查数仓。

不要跳步，也不要按 SKU 前缀去匹配。

1. 产品 SKU `BP265-NR71BA`。
2. `lute_edw.dim_scm_sku_info_df` 得到 `BP265-NR71BA-A` 和 `BP265-NR71BA-B`。这是同一个产品的两家供应商，不是两个商品。前缀匹配会碰到标签 SKU `BP265-NR71BA-01US`。
3. `lute_edw.dim_sal_sku_info_df` 拿出渠道、站点、店铺、`sale_sku_code`、ASIN、产品 SKU、供应链 SKU。字段名是 `sale_sku_code`，不是 `platform_sku`。
4. Amazon 页面和评论用 ASIN，不用产品 SKU。这条是 `B0DTYSLFLX`，没有 parent ASIN。描述和卖点是空的，不要显示成要点。
5. 积加的 `sku` 等于供应链 SKU（带 `-A` / `-B`）。`msku` 等于 `sale_sku_code`，并且 `country` 等于站点。
6. Walmart item 用积加 `item_id` `5468700454`，不用 ASIN。店铺 SKU `WM-MC-US-01-BP223-NR71BA` 字符串里嵌了另一个 BP 码，不要从字符串里拆。US 对应 `BP265`。MX 是 0.84 / 0.16 的拆分，不是整只。
7. Shopify 上这一只是 0 行。能打开的页面是相邻 SKU `BP266-NR71BA-A`，变体 `43846410830022`，`product_id` `8189195354310`。Okendo 的 `product_sku` 是 Shopify 的数字商品 id，不是公司 SKU。
8. 工单按 `platform_sku`：`RT-US-M9NEW-Pink2` 和 `RT-US-M9NEW-B`。`CL-US-M9NW-Pink2` 是 0。
9. 设计文件先用 `lute_edw.dwd_pd_design_task_relation_product_df` 的 `product_spu = 'SPU000168'`，再按 `design_task_code` 接 `lute_edw.dwd_pd_design_task_file_df`。23 个任务，63 个 `oss_key`。
10. `dwd_pd_sop_product_materiel_df` 对 `BP265-NR71BA` 和 `SPU000168` 都是 0 行。`dwd_sal_lute_product_sku_df` 的主图是 Excel `DISPIMG`，`product_images` 和 `cleaning_instructions` 是空的。

查的时候项目名用 `lute_edw` 或 `lute_app_dw`。`lute_dw` 会被拒，服务要的是项目名，不是库名。只读 `SELECT`。服务端会自己加 `LIMIT`。`COUNT` 的别名不要用 `files`，这个词会被当成保留字，用 `file_cnt`。数组展开用 `CROSS JOIN UNNEST(split(...))`。`LATERAL VIEW explode` 在这套库上没跑通。

目录检索走 find-table，`user_token` 传空字符串。目录里有一张表，不代表当前身份能查它。

核对时算过的完整率，进度表是它的压缩：

| 对象 | 完整率 | 分母是什么 |
|---|---|---|
| 公司主档 | 1/1 | 这一只 SKU |
| 公司主图 | 0/1 | 字段在，值打不开 |
| 供应链编码 | 2/2 | `-A` / `-B` |
| 销售映射 | 56/56 | 映射行 |
| 映射行上的 Amazon ASIN | 21/21 | 应有 ASIN 的映射行 |

| Walmart 图片 | 1/3 | 店铺 SKU |

映射一共 56 行、7 个 ASIN、38 个 sale SKU。其中 13 个 sale SKU 的字符串里嵌了别的 BP 码。销量、库存、退货能关联上，但那不是字段空值率，所以上表没有给它们写一个分数。

## 7. 没做

这些不是遗漏后的默认下一步。要做的话先单独定。

- 数仓查询没有接进 API。快照是查完之后写进 fixture 的。
- 没有竞品评论。缺一份竞品 ASIN 名单，不从评论表里把别的 ASIN 倒出来。
- 没有广告花费。那些表不是素材库。
- 没有把缺口分给负责人。数仓里没有这份名单。
- 没有发版，没有改生产。
- `.env` 和数仓的访问凭据不在这个分支里。
- 浏览器自动化填登录密码被审核拦住过。页面核对是在已经登录的会话里做的。
